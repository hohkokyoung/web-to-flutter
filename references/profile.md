# The project profile

One file per repo, `.claude/web-to-flutter.md`, read at the start of every run. It's
what makes this skill fit the project.

## Creating it (first use in a repo)

### 1. Scan (read-only)

Find what you can; don't ask yet.

**Web side**
- Framework: from `package.json` (next, react, vue, svelte, astro…) or plain HTML.
- Where pages and components live, and how routes map to files.
- Styles:
  - global CSS, CSS modules, Tailwind config;
  - CSS variables (`:root { --… }`);
  - design docs (DESIGN.md, a style guide, a Figma link in the README).
- The data layer: an API client file, fetch wrappers, an OpenAPI or GraphQL schema.
- The dev server command and port.

**Flutter side** (`pubspec.yaml` anywhere in the repo)
- Flutter version (`.fvmrc`, `.tool-versions`, CI files).
- State management: riverpod, bloc, provider, signals…
- Router: go_router, auto_route, Navigator.
- HTTP and API client: dio, retrofit, openapi-generator, chopper, plain http.
- Theme and tokens: the `ThemeData` file, any generated tokens.
- Shared widgets: a `widgets/` or `ui/` folder. List each public widget with one line
  on what it's for.
- Tests: `test/` helpers, a fake backend or mocks, fixtures, golden tests.
- Platforms present (ios/, android/), bundle id (`ios/Runner.xcodeproj` /
  `Info.plist`), and simulator or run commands (a Makefile, scripts, README).

**Process**
- Lint and test commands (Makefile, package scripts, CI).
- A spec or change process (`openspec/`, RFC folders, ADRs in `docs/decisions`).
- Docs that describe screens (`docs/`, README sections).
- Agent instructions (CLAUDE.md, AGENTS.md). Their rules apply too.

### 2. Draft

Fill the template below. Mark anything inferred rather than read as **(guess)**. Leave
a field as `?` when nothing was found.

### 3. Ask only the gaps

Usually two to four short questions, often these:

1. **Look:** match the website closely, or adapt it to native conventions?
2. **Platform feel:** iOS feel on both platforms (no ripples, Cupertino transitions and
   controls), Material 3, or adaptive per platform?
3. **Business rules** that live in the web client: move them to the backend so both
   clients share them, or mirror them in Dart?
4. **No Flutter app yet:** propose the stack from `flutter.md` and where to put the
   app; ask before creating it.

Use the AskUserQuestion tool, with the recommended option first.

### 4. Confirm and save

Show the draft, apply corrections, save `.claude/web-to-flutter.md`, and commit it with
the work it came with. If the repo has a CLAUDE.md, add one line pointing to the
profile and this skill.

## Keeping it current

At the end of each run, add to the profile when one of these happens:

- **A new shared widget:** add a line to the widget table.
- **A design decision from the user:** add a line under House rules, in their terms,
  with the date. For example: "Lists cut off cleanly under a fixed header; no fade
  (rejected 2026-10-10)."
- **A rejected approach:** record it, so it isn't proposed again.
- **A changed command, path or version:** fix it.

Keep it short: one line per fact. If a section passes about 40 lines, tighten it.

## Template

```markdown
# web-to-flutter profile: <project>

## Repo
- Web: <framework> in `<path>`; styles `<path>`; tokens/design doc `<path>`; dev server `<cmd>` → <url>
- App: Flutter <version> (`<fvm|flutter>`) in `<path>`; platforms <ios/android>; bundle id `<id>`
- Backend/API: <what, where>; app client generated by `<cmd>` from `<schema>` | hand-written in `<path>`

## Stack
- State: <…>  · Router: <…>  · HTTP/client: <…>  · Images: <…>
- Theme: `<path>` (tokens `<path>`, generated by `<cmd>` | hand-written)

## Commands
- Run web: `<cmd>` · Run app (simulator): `<cmd>` · Build for simulator: `<cmd>`
- Test app: `<cmd>` · Test backend: `<cmd>` · Lint: `<cmd>` · Codegen: `<cmd>`

## Tests
- Harness: `<path>` (how to pump the app) · Fake backend: `<path>` · Fixtures: `<path>`
- Gotchas: <…>

## Shared widgets (reuse these)
| Widget | File | Use |
|---|---|---|

## House rules
- Look: <match website closely | adapt>
- Platform feel: <iOS on both | Material 3 | adaptive>
- Business rules: <server-side, both clients read them | mirrored in Dart>
- <settled decisions, one line each, dated>

## Rejected
- <approach — why, date>

## Process
- Specs: <OpenSpec | none> · Docs to update: `<paths>` · Commit/push: <rules>
```
